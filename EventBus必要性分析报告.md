## 二、EventBus 设计复杂度 vs 实际需求

┌───────────────────────────────────────────────────────────────────┐
│                    过度设计的具体表现                             │
│                                                                   │
│  1. 预定义事件常量 (GameplayEvents类):                            │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ 定义了33个预定义事件常量，包括:                         │   │
│     │ - 伤害类: 4个 (OnDamageReceived, OnDamageDealt等)       │   │
│     │ - 治疗类: 2个 (OnHealingReceived, OnHealingDealt)       │   │
│     │ - 技能类: 6个 (激活、结束、取消、失败、冷却等)          │   │
│     │ - 标签类: 3个 (添加、移除、计数变化)                    │   │
│     │ - 效果类: 5个 (应用、移除、激活、停用、堆叠变化)        │   │
│     │ - 属性类: 3个 (变化、预变化、后变化)                    │   │
│     │ - 状态类: 4个 (死亡、复活、危险、资源耗尽)              │   │
│     │ - 战斗类: 3个 (开始、结束、目标变化)                    │   │
│     │                                                         │   │
│     │ 问题: 这些常量几乎没有被实际使用!                       │   │
│     │ ASC中使用的都是硬编码字符串，如"Damage.Dealt"           │   │
│     └─────────────────────────────────────────────────────────┘   │
│                                                                   │
│  2. 线程安全设计:                                                 │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ 使用lock (_lock)保护所有操作                            │   │
│     │ 复制处理器列表避免并发修改                             │   │
│     │                                                         │   │
│     │ 问题: Unity是单线程运行，不需要线程安全!                │   │
│     │ 这增加了不必要的复杂度和性能开销                       │   │
│     └─────────────────────────────────────────────────────────┘   │
│                                                                   │
│  3. 丰富的API接口:                                                │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ 提供了大量方法:                                         │   │
│     │ - Subscribe/Unsubscribe                                 │   │
│     │ - Publish (两个重载版本)                                │   │
│     │ - HasSubscribers/GetSubscriberCount                     │   │
│     │ - ClearAll/ClearEvent                                   │   │
│     │ - GetRegisteredEvents                                   │   │
│     │                                                         │   │
│     │ 问题: 实际只用到了Subscribe、Unsubscribe、Publish!      │   │
│     │ 其他方法完全没有被调用                                 │   │
│     └─────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────────┘

## 三、EventBus 的唯一实际用途分析

┌───────────────────────────────────────────────────────────────────┐
│                GameplayEffectSpec 事件监听的真实需求               │
│                                                                   │
│  唯一的订阅者: GameplayEffectSpec.SetupEventListeners()            │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ 功能: 为ExecutionCalculation的EventExecutionCondition       │   │
│  │       注册事件监听器                                       │   │
│  │                                                             │   │
│  │ 代码逻辑:                                                   │   │
│  │ foreach execution in GameplayEffect.Executions:            │   │
│  │     foreach condition in execution.EventConditions:        │   │
│  │         eventName = condition.EventName                    │   │
│  │         handler = (eventData) => {                         │   │
│  │             if (condition.ShouldTrigger(eventData))        │   │
│  │                 condition.TriggerEvent(spec, eventData)    │   │
│  │         }                                                   │   │
│  │         GameplayEventBus.Instance.Subscribe(eventName, handler)│   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                   │
│  应用场景举例:                                                    │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ 1. 反击技能: 监听"Damage.Taken"事件                         │   │
│  │    当受到伤害时自动触发反击ExecutionCalculation             │   │
│  │                                                             │   │
│  │ 2. 治疗加成: 监听"Healing.Received"事件                     │   │
│  │    当接受治疗时额外触发治疗加成效果                         │   │
│  │                                                             │   │
│  │ 3. 连击系统: 监听"Ability.Activated"事件                    │   │
│  │    当释放特定技能时触发连击效果                             │   │
│  │                                                             │   │
│  │ 4. 属性联动: 监听"Attribute.Changed.Health"事件             │   │
│  │    当生命值变化时触发其他属性的调整                         │   │
│  └─────────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────────┘

## 四、不使用EventBus的替代方案分析

┌───────────────────────────────────────────────────────────────────┐
│                     替代方案的可行性分析                          │
│                                                                   │
│  方案一: 直接回调机制                                             │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ 在AbilitySystemComponent中维护事件委托:                     │   │
│  │                                                             │   │
│  │ public event Action<GameplayEventData> OnDamageDealt;       │   │
│  │ public event Action<GameplayEventData> OnDamageReceived;    │   │
│  │ public event Action<GameplayEventData> OnAbilityActivated;  │   │
│  │ // ... 其他事件                                             │   │
│  │                                                             │   │
│  │ GameplayEffectSpec直接订阅ASC的事件:                        │   │
│  │ Owner.OnDamageReceived += HandleDamageEvent;                │   │
│  │                                                             │   │
│  │ 优势:                                                       │   │
│  │ ✓ 更直接，性能更好                                         │   │
│  │ ✓ 编译时类型检查                                           │   │
│  │ ✓ 更好的IDE支持 (跳转、重构等)                             │   │
│  │ ✓ 无需字符串事件名，减少错误                               │   │
│  │                                                             │   │
│  │ 劣势:                                                       │   │
│  │ ✗ 需要为每种事件类型定义委托                               │   │
│  │ ✗ 跨ASC事件传递需要额外处理                                │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                   │
│  方案二: 观察者模式 (简化版EventBus)                              │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ class SimpleEventBus {                                      │   │
│  │     private Dictionary<string, List<Action<object>>> events;│   │
│  │                                                             │   │
│  │     public void Subscribe(string eventName, Action<object> handler) {│   │
│  │         if (!events.ContainsKey(eventName))                 │   │
│  │             events[eventName] = new List<Action<object>>();  │   │
│  │         events[eventName].Add(handler);                     │   │
│  │     }                                                       │   │
│  │                                                             │   │
│  │     public void Publish(string eventName, object data) {    │   │
│  │         if (events.TryGetValue(eventName, out var handlers))│   │
│  │             foreach (var handler in handlers)               │   │
│  │                 handler(data);                              │   │
│  │     }                                                       │   │
│  │ }                                                           │   │
│  │                                                             │   │
│  │ 优势:                                                       │   │
│  │ ✓ 保持现有架构不变                                         │   │
│  │ ✓ 代码量减少90%                                            │   │
│  │ ✓ 无线程安全开销                                           │   │
│  │ ✓ 更简单易懂                                               │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                   │
│  方案三: 完全移除EventBus                                         │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ 将ExecutionCalculation的事件条件改为轮询检查:                │   │
│  │                                                             │   │
│  │ 在GameplayEffectSpec.Tick()中:                              │   │
│  │ foreach execution in GameplayEffect.Executions:            │   │
│  │     foreach condition in execution.EventConditions:        │   │
│  │         if (condition.CheckCondition(Owner))               │   │
│  │             execution.Execute(...)                         │   │
│  │                                                             │   │
│  │ 优势:                                                       │   │
│  │ ✓ 架构最简单                                               │   │
│  │ ✓ 无事件管理开销                                           │   │
│  │ ✓ 更容易调试和理解                                         │   │
│  │                                                             │   │
│  │ 劣势:                                                       │   │
│  │ ✗ 每帧都要检查条件，性能略差                               │   │
│  │ ✗ 无法响应瞬时事件                                         │   │
│  │ ✗ 失去事件驱动的灵活性                                     │   │
│  └─────────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────────┘

## 五、性能影响分析

┌───────────────────────────────────────────────────────────────────┐
│                    EventBus 的性能开销分析                        │
│                                                                   │
│  1. 内存开销:                                                     │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ • Dictionary<string, List<Action<GameplayEventData>>>    │   │
│     │ • 每个事件名的字符串存储                                │   │
│     │ • Action委托链的内存分配                                │   │
│     │ • GameplayEventData对象的频繁创建                       │   │
│     │                                                         │   │
│     │ 估算: 每个注册事件约占用 200-500 bytes                  │   │
│     │ 对于大型项目可能有数百个事件监听器                     │   │
│     └─────────────────────────────────────────────────────────┘   │
│                                                                   │
│  2. CPU开销:                                                      │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ • lock操作的同步开销 (每次Subscribe/Publish)            │   │
│     │ • Dictionary字符串查找 O(1) 但有哈希计算               │   │
│     │ • List<Action>的复制操作 (每次Publish)                  │   │
│     │ • 异常处理的try-catch开销                               │   │
│     │ • GameplayEventData对象创建和GC压力                    │   │
│     │                                                         │   │
│     │ 每次事件发布约需要: 50-100微秒                          │   │
│     │ 高频事件(如属性变化)可能影响帧率                       │   │
│     └─────────────────────────────────────────────────────────┘   │
│                                                                   │
│  3. 与简化方案的性能对比:                                         │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ 当前EventBus:     100% (基准)                           │   │
│     │ 直接委托:         ~30% (无字典查找，无对象创建)          │   │
│     │ 简化EventBus:     ~60% (无锁，无复制，简单数据)          │   │
│     │ 轮询检查:         ~80% (无事件开销，但有检查开销)        │   │
│     └─────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────────┘

## 六、架构设计问题分析

┌───────────────────────────────────────────────────────────────────┐
│                    EventBus 引入的设计问题                        │
│                                                                   │
│  1. 隐式依赖关系:                                                 │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ 问题: 事件的发布者和订阅者之间没有明确的接口约定        │   │
│     │                                                         │   │
│     │ 表现:                                                   │   │
│     │ • 无法通过代码静态分析找到事件的所有使用者              │   │
│     │ • 重构时容易遗漏事件名的更新                           │   │
│     │ • 新人难以理解系统间的依赖关系                         │   │
│     │                                                         │   │
│     │ 示例:                                                   │   │
│     │ ASC发布"Damage.Dealt"事件，但无法知道谁在监听          │   │
│     │ GameplayEffectSpec监听事件，但事件名是运行时确定的      │   │
│     └─────────────────────────────────────────────────────────┘   │
│                                                                   │
│  2. 调试困难:                                                     │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ 问题: 事件驱动的逻辑难以追踪和调试                     │   │
│     │                                                         │   │
│     │ 表现:                                                   │   │
│     │ • 无法在IDE中直接跳转到事件处理代码                    │   │
│     │ • 运行时才能确定事件是否被正确处理                     │   │
│     │ • 事件处理异常被捕获，可能隐藏真正的问题               │   │
│     │                                                         │   │
│     │ 调试场景:                                               │   │
│     │ "为什么这个效果没有触发?" → 需要检查事件名拼写        │   │
│     │ → 检查是否正确订阅 → 检查事件是否被发布                │   │
│     └─────────────────────────────────────────────────────────┘   │
│                                                                   │
│  3. 过度抽象:                                                     │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │ 问题: 为了一个简单需求引入了复杂的通用解决方案          │   │
│     │                                                         │   │
│     │ 实际需求: GameplayEffectSpec需要响应特定事件            │   │
│     │ 当前方案: 通用的全局事件总线                           │   │
│     │                                                         │   │
│     │ 这类似于: 为了在房间里传话而安装了全城广播系统         │   │
│     │                                                         │   │
│     │ 后果:                                                   │   │
│     │ • 增加了学习成本                                       │   │
│     │ • 增加了维护复杂度                                     │   │
│     │ • 性能不是最优的                                       │   │
│     └─────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────────┘

│  ┌─────────────────────────────────────────────────────────────┐   │

│  │ 改为在ASC中直接提供类型安全的事件委托                       │   │
│  │ 这将提供最佳的性能和开发体验                               │   │
│  └─────────────────────────────────────────────────────────────┘   │
